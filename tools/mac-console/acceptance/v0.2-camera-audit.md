# V0.2 camera observation audit

Audit date: 2026-10-13. This record separates repository-declared interfaces from the NUC runtime evidence available during this implementation.

## Verified interfaces in the repository

- `tzb_ws/src/pose_estimator/config/camera_switch.yaml` selects an Orbbec Gemini 336L by default (with a RealSense D435i alternative), both configured for 640×480 at 30 FPS.
- `camera_switch.launch.py` normalizes the RGB and registered depth image topics to `/camera/color/image_raw` and `/camera/depth/image_rect_raw`, both `sensor_msgs/msg/Image`.
- `yolo_node` consumes `/camera/color/image_raw`. Its optional `/yolo/annotated_image` output is also `sensor_msgs/msg/Image`; the detector only draws and publishes that output when it has a subscriber. The Console Agent's read-only subscription therefore adds annotation work while the Agent runs, but does not start or change the detector.
- The Console Agent subscribes only to those three fixed topics with sensor-data QoS. It exposes fresh frames through the existing `127.0.0.1:8765` listener and fixed SSH forward. It stores the latest frame in memory, rejects stale frames after 1.5 seconds, and accepts no caller-selected topic or write operation.
- Receive FPS is measured from Agent callback arrival times. `frame_age_ms` uses the NUC monotonic clock. `header_to_agent_ms` compares ROS event time to the NUC receipt time and is explicitly clock-dependent. `gap_events` counts gaps longer than 1.5 seconds; it is not an exact dropped-frame counter. The depth preview is per-frame grayscale normalization and is not a metric scale.

## NUC and Mac runtime evidence

- Mac: Apple Silicon (`arm64`), macOS 26.6. The native app built and opened; its default screen is the Test Cockpit.
- NUC: Ubuntu 22.04.5 LTS, Python 3.10.12, ROS 2 Humble present. The checked NUC checkout reports `6a48dc5` and is clean; no Console Agent was listening on port 8765 before this audit.
- The NUC has no `/dev/video*` device. The attached USB inventory did not show the configured Orbbec or RealSense camera. The active vision processes observed during the audit came from temporary `/tmp/lunar-p9i` test builds and used namespaced `/p9i_<id>/image` topics; these are not treated as a physical camera stream.
- The V0.2 Agent was copied to a temporary `/tmp` directory and started with the NUC's `/usr/bin/python3` and sourced Humble environment. It bound to `127.0.0.1:8765`; `GET /health` returned HTTP 200, `/v1/vision` returned HTTP 200 with RGB/depth/YOLO all `unavailable` and null FPS/timestamps, and the RGB frame route returned HTTP 503 with `ROS Topic 当前没有发布者`.
- The rebuilt Mac app connected to that temporary Agent over the existing SSH forward and rendered the three sources as unavailable without a cached frame or fabricated metrics. Stopping the Agent cleared the live readings; restarting it restored the connection and the same accurate unavailable states.
- No camera, ROS bringup, control node, actuator, or robot device was started for this audit. The temporary Agent was stopped after the connection-recovery check; it was not installed as a service or copied into the NUC repository.

## V0.2a isolated synthetic-source acceptance (2026-10-13)

Scope: **synthetic ROS Images only**, not real camera/algorithm acceptance. The only added publishers are the opt-in test fixture at `tools/console-agent/acceptance/synthetic_publisher.py`. They run on NUC with `ROS_DOMAIN_ID=203`, `ROS_LOCALHOST_ONLY=1` and ROS Humble sourced. The Agent uses the same isolated domain; no robot overlay, sensor bringup, motor, controller, or physical device is started. Agent and fixture are copied to a temporary `/tmp/lunar-v02a-203-20261013` directory, not into the NUC repository.

- NUC: Agent bound to `127.0.0.1:8765`, exposed to Mac through fixed SSH loopback forwarding. Synthetic `rgb8`, `16UC1`, and `rgb8` annotated placeholder topics appeared as `streaming`; `frame_id` reported `lunar-v0.2a-synthetic/{rgb|depth|yolo}`. Agent receive rate was about **9.8 FPS**, not camera FPS.
- Mac: all three `GET /v1/vision/{id}/frame.png` calls over SSH returned uncached HTTP 200 `image/png`, 64×48, with distinct content. The rebuilt and launched Mac app established its own `127.0.0.1:18765` SSH forward to the NUC; its forwarded `/v1/vision` returned all three synthetic stream states. A native Swift test harness decoded the actual forwarded PNGs and rendered each selected source via the production `TestCockpitView` into three distinct offscreen GUI images. Direct state regression also passed RGB→depth→YOLO selection, delayed old-source rejection, session restart, stale image clearing, and locally measured Mac image-update rate.
- Pausing the synthetic publisher (without removing its ROS graph registration) for over 1.5 seconds yielded `stale` for all three streams and HTTP 503 for all frame endpoints; resuming publishing returned all three to `streaming`, each recording one receive-gap event. Agent unit tests also guard against reusing a cached frame if a publisher disappears and quickly reappears.
- Depth preview converts at most 1024×1024 sampled pixels, including for larger `16UC1` input; it no longer allocates a whole-frame list of Python integers. A 2048×2048 depth payload regression checks PNG size/pixels and less than 16 MiB of conversion-only Python allocations (caller-provided ROS bytes excluded). Agent/API/encoding tests **23/23 pass**.
- Mac source typecheck and native app build pass using compatible SDK 26.5. Standard SwiftPM tests cannot start due the pre-existing `swift-package` / `BuildServerProtocol` dynamic-library mismatch; direct Swift model and offscreen-render regression programs pass. macOS accessibility/screen-capture permission prevented screenshotting the live window; the actual data-fed SwiftUI render path was exercised offscreen instead.

`frame_rate_hz` is **NUC callback receive FPS**. The GUI's separate **Mac image-update FPS** counts successfully accepted replacement frames (bounded by the current 500 ms polling loop, nominally at most ~2 FPS); it is not the monitor's physical refresh rate. Synthetic frames are visibly marked as such via their ROS `header.frame_id`; unverified ROS streams are not presented as proven camera hardware.

## Remaining V0.2b physical acceptance

**Not verified:** Orbbec RGB hardware acquisition, depth accuracy/geometry, live YOLO inference or detection quality, actual production image throughput and long-running load/latency. V0.2b must confirm physical connection and publisher provenance, then measure a genuine NUC camera RGB frame through Mac GUI (sustained local FPS and round-trip latency), and separately validate depth and YOLO. V0.2a alone does not authorize bringing up hardware or physical motion.
