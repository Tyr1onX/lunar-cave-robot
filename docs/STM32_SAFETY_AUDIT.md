# STM32 control safety audit

Audit basis: the findings below were first recorded against the P9-B branch base. The P9-C branch adds offline safety state machines and host tests described in [P9-C safety state machines](P9C_SAFETY_STATE_MACHINES.md). No serial port, motor, controller, or robot was connected. This report identifies code paths; it does not claim a safety-rated design or successful physical stop.

## P9-C source-level disposition

P9-C addresses the software behaviors behind `CHASSIS-01`, `ARM-01`, `ARM-03`, and `ARM-06` in source: the chassis no longer sends startup enable frames; its command gate remains closed until the operator completes a neutral re-arm sequence; receiver/serial/UART faults latch; arm target adoption has a 100 ms lease, and RC loss, host disable, stale command, or source change latches the arm held until manual re-arm. The existing 14-byte chassis and 46-byte arm command layouts remain unchanged.

These changes do not close the physical S0 gate. The chassis sends a CAN relax command while disarmed, and the arm sends motor disable commands while held; the real drive response, braking/holding behavior, and mechanical support are not established. The arm may fall when torque is removed. Both firmwares still lack end-to-end measured-stop acknowledgement. Keep powered motion blocked pending the hardware-owner review listed in `P9C_SAFETY_STATE_MACHINES.md`.

The policy modules and chassis production parser path have host tests. The arm test covers the pure C policy, not the full product integration. The arm firmware build remains blocked by missing XRobot-generated files. Therefore the P9-C changes are source-level mitigations with offline unit evidence, not verified control safety.

## Severity definitions

- **S0 — block any real actuator motion test:** source does not establish that the requested disable/stop reaches the motor or that startup is fail-safe. Resolve and independently verify before permitting powered motion.
- **S1 — high risk; resolve before supervised motion:** loss, corruption, stale feedback, motor fault, or command-delivery failure can remain undetected or inadequately handled.
- **S2 — observability / defense in depth:** improves traceability and fault diagnosis; cannot substitute for the S0/S1 controls.

## Existing mitigations confirmed in code

- Chassis CH8 selection gates the serial command path and a separate shared safety gate; SBUS loss maps to disabled mode. A valid serial frame is not enough by itself to open that gate.
- Chassis controller checks a 200 ms command age at a 5 ms control interval and commands zero setpoints/relax frames when the command is absent, disabled, or stale.
- Arm host parser requires a complete frame with header, both sync bytes, trailer, finite values for all six joints, host enable, and S2 host-control mode before adopting targets. Joint code has software position, velocity and acceleration bounds, but no independently verified current ceiling or feedback-freshness interlock. The disabled frame is not a stop request; it is ignored for target adoption.
- Arm joint code applies configured position limits, velocity/acceleration planning bounds, finite-value checks, and tracking windows (`others/src/obj/roboarm.cpp`, `variables.cpp`). These software bounds are present, but no per-joint feedback freshness/fault interlock or independent verified current limit is established by the host protocol.
- Arm remote error task holds/disabled motors when both remote switches request emergency stop or valid RC frames are absent for 3 seconds; it continues disabled feedback keepalive while held.
- ROS P4f lifecycle/epoch barriers and PTY tests protect host-side command handling. They do not close the MCU USB-loss gap.

These mitigations reduce some software-path risks but do not prove a safety-rated stop, motor-disabled state, or real hardware interlock.

## Release gate

**No real actuator motion is cleared by this audit.** S0 findings remain open. Do not flash firmware, open controller serial/USB, enable motor power, or start robot motion under this change. A separate hardware safety review must confirm the physical E-stop/power cutoff, safe startup, watchdog/reset behavior, drive disable response, measured stopping, and device firmware identity.
